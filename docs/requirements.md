# Requirements Specification
## DLSU Student Handbook RAG Chatbot

**Document status:** v1.1 — open items resolved; approved direction
**Prepared by:** Requirements Engineer
**Date:** 20 July 2026

---

## 1. Project Overview

This project develops a locally executed, terminal-based chatbot that answers natural-language questions about the De La Salle University (DLSU) Student Handbook (AY 2021–2025 edition) using Retrieval-Augmented Generation (RAG) with a Small Language Model (SLM). The system is intended to replace manual searching of the 339-page handbook and to serve as an undergraduate academic project that is understandable, well documented, and extensible.

This project supersedes an earlier fine-tuning approach (GPT-2 with LoRA), following adviser guidance to adopt RAG. The architectural contrast between fine-tuning and retrieval-augmentation is retained as discussion material for the accompanying paper and presentation.

## 2. Source Document Profile

Analysis of the provided PDF (`student-handbook.pdf`) established the following:

| Property | Finding |
|---|---|
| Pages | 339 |
| Format | Native (text-based) PDF; Adobe InDesign export; all fonts embedded with Unicode maps |
| OCR required | No |
| Corpus size | ~84,000 words (~110,000–120,000 tokens) |
| Structure | Table of Contents; named sections (e.g., "Section 5: Lasallian Community Standards"); hierarchically numbered provisions (e.g., 5.3.1.1.6) |
| Edition | Academic Year 2021–2025 |
| Known artifacts | Cover pages, acknowledgement form, front-matter messages, and in-text running page numbers require cleaning prior to chunking |

The hierarchical numbering scheme enables section-level citation without dependence on physical page numbers.

## 3. Functional Requirements

- **FR-1. Question answering.** The system shall accept free-form English questions in a terminal interface and return answers grounded exclusively in the handbook corpus.
- **FR-2. Retrieval-augmented generation.** Answers shall be generated by an SLM conditioned on retrieved handbook passages; the model shall not answer from parametric knowledge alone.
- **FR-3. Citations.** Every answer shall cite its source at minimum to the handbook section (section number and/or heading). Page numbers shall be included where reliably recoverable but are not required (per stakeholder decision).
- **FR-4. Refusal behavior.** When the handbook does not contain information relevant to a question, the system shall issue a polite refusal stating that the topic is not covered, rather than speculating.
- **FR-5. Answer style.** Answers shall be phrased in plain, student-friendly English where faithful simplification is possible; where policy wording is precise or legally significant (e.g., disciplinary provisions), the system shall quote or closely paraphrase the handbook text.
- **FR-6. Independent queries.** Each question shall be treated independently. Conversation memory is out of scope for version 1 and is recorded under Future Work.
- **FR-7. Ingestion pipeline.** The system shall provide a repeatable offline pipeline: PDF parsing → cleaning → chunking → embedding → vector storage.
- **FR-8. Terminal interface.** Version 1 shall operate as a command-line application with a simple interactive loop (ask, answer, repeat, exit command).

## 4. Non-Functional Requirements

- **NFR-1. Local-first execution (revised).** All data processing — ingestion, chunking, embedding, storage, and retrieval — shall run locally on the target machine. The sole external dependency is the generation API call (see AC-1); no handbook data leaves the machine except retrieved passages sent within generation prompts.
- **NFR-2. Hardware envelope.** Target hardware: 16 GB RAM; NVIDIA GTX 1650 (4 GB VRAM); frequent CPU-only operation. Model selections (SLM and embedding model) must operate within this envelope, implying a quantized SLM in approximately the 1–4 B parameter range.
- **NFR-3. Factual correctness over creativity.** Generation settings and prompts shall prioritize grounded, deterministic-leaning output (e.g., low temperature).
- **NFR-4. Latency.** Interactive use should target end-to-end response times acceptable for a demo on CPU (indicative goal: under ~30 seconds per answer; to be benchmarked and recorded honestly in testing.md).
- **NFR-5. Maintainability and readability.** Code shall follow the documented style guide: file-level documentation blocks, function docstrings, meaningful names, and modular structure.
- **NFR-6. Documentation.** All design decisions shall be recorded in the `docs/` folder and kept current at every phase.
- **NFR-7. Language.** English input and output only.

## 5. Architectural Constraints and Decisions

- **AC-1. Pluggable LLM backend — API primary (resolved).** The generation component shall be implemented behind a single interface. The **primary backend is API-based** (key-based hosted model), per stakeholder decision and adviser guidance. The interface shall permit a local backend (quantized SLM via Ollama/llama.cpp) to be added later without architectural change; the local backend is recorded under Future Work. Retrieval components (embedding model, vector store) remain fully local regardless of generation backend.
- **AC-2. Modularity.** Ingestion, chunking, embedding, storage, retrieval, prompting, generation, and interface concerns shall reside in separate modules with defined interfaces.
- **AC-3. Multi-document readiness.** Metadata schema and storage design shall accommodate additional university documents (academic calendar, registrar policies, scholarship handbook, etc.) without architectural change; v1 ingests only the Student Handbook.
- **AC-4. Terminal-first.** The interface layer shall be thin enough that a future GUI or web front end can reuse the retrieval and generation core unchanged.

## 6. Out of Scope (Version 1)

- Conversation memory / multi-turn context
- Local SLM generation backend (deferred; interface-compatible)
- Non-English input handling
- OCR of scanned documents
- GUI or web interface
- Reranking models (recorded as future retrieval improvement)
- Ingestion of documents other than the Student Handbook

## 7. Open Items

- **OI-1. Resolved:** API backend selected as primary; local backend deferred to Future Work behind the same interface.
- **OI-2. Resolved:** Handbook edition ("AY 2021–2025") displayed once in the session start-up banner.

## 8. Acceptance Criteria (v1)

1. Given a question answerable from the handbook, the system returns a correct answer with at least a section-level citation.
2. Given a question not covered by the handbook, the system politely refuses.
3. The full pipeline (ingest through chat) runs on the target hardware without external services when using the local backend.
4. Each pipeline phase can be executed and tested independently.
5. All documentation files enumerated in the project plan exist and reflect the implemented system.
